Session 01 · Stages 1–2

etl/base_meds.py + etl/meds_reader_db.py

MIMIC-IV → MEDS, and MEDS → the meds_reader database. 189 lines, 4 functions, 4 test files.

Map

These are the only two stages that wrap a third-party console script. Everything from stage 2.5 onward is our own Polars code.

FileStageWrapsIn → out
base_meds.py1meds_etl_mimicraw MIMIC-IV CSVs → MEDS long-format parquet shards
meds_reader_db.py2meds_reader_convertthose shards → the column store meds_reader queries

Neither library exposes a Python API. That single fact determines the entire design of both files.

Walk

build_command(src, dest, *, executable, num_shards=100, num_proc=1, backend="cpp") -> list[str]

Pure. Touches no filesystem. Validates, then returns argv:

[exe, src, dest, "--num_shards", "100", "--num_proc", "1", "--backend", "cpp"]
  • The * makes everything after it keyword-only. src and dest stay positional to mirror the CLI — but swapping them makes the ETL read your output as its input, so test_build_command_orders_positionals_source_before_destination does nothing but assert args[1] == src and args[2] == dest.
  • Everything is str()-ed. subprocess accepts PathLike in argv on POSIX, so a leaked Path works here and breaks silently elsewhere. test_build_command_returns_only_strings closes it.
  • Validation lives here, not in the runner — backend not in _BACKENDS, num_shards < 1 or num_proc < 1, both ValueError. A typo fails in microseconds instead of after launch.

run_base_meds(src, dest, *, executable=None, ...) -> Path

Three guards, then exactly one child process.

  1. Version subfolder — (src / "2.2").is_dir(). meds_etl_mimic wants the parent of the version folder. Pointing at mimic_data/2.2 directly is the classic mistake.
  2. No overwrite, ever — dest.exists() → FileExistsError. A multi-hour job that half-overwrites looks finished and is unrecoverable.
  3. Executable resolution — injected, else shutil.which, else FileNotFoundError naming .venv-modelling/bin/meds_etl_mimic.

Then subprocess.run(cmd, check=True); return dest. No capture_output, no stdout=, no stderr=.

build_db_command / run_meds_reader_convert

Structurally identical. One flag (--num_threads) instead of three; the guard checks src / "data". The symmetry is deliberate: learn one and you have learned both, and a reviewer comparing them spots a divergence instantly.

Decisions

Why split build_*_command from run_*?

The pure half is verifiable with no filesystem, no binary, and no process — all five parametrized cases run in microseconds and CI needs nothing installed. And argv can be diffed against the real meds_reader_convert --help output without launching it, which is how the signature was actually verified: positional source_dataset, positional destination_database, --num_threads INT [1].

Why is output never captured?

capture_output=True buffers the child's stdout in memory until it exits: nothing visible for four hours, and possibly an OOM on the buffer. The log comes from the shell, not Python — the driver docstring's 2>&1 | tee ~/meds_etl_$(date +%F_%H%M).log, which writes to terminal and file at once. Capturing cannot do both.

Why check=True, and why is the executable injectable?

check=True because these are hand-run one-off jobs and the traceback is the error report; a silent non-zero exit leaves a partial dataset that looks complete.

The executable is injectable because there are two virtualenvs, split on numpy (pyhealth needs ≥ 2.2, femr needs < 2). PATH may point at either, so the driver passes Path(sys.executable).with_name("meds_etl_mimic") — the console script from the same venv as the interpreter that imported the library. shutil.which is only the interactive fallback.

Why is parallelism a CLI flag, not our own process pool?

Each run_* launches exactly one child, which parallelises internally; we never manage workers or their failure modes. Note num_proc is the sort stage's process count and num_shards is the output partition count — different things. The driver overrides shards to 200 (the library default is the tool's 100) because shard count is what stage 2's --num_threads fans out over, and what caps peak memory in every downstream stage.

Traps

Trap · the "2.2" symlink

We run MIMIC-IV 3.1. mimic_data/2.2 is a symlink to mimic-iv-3.1 because the tool hardcodes the path and will not look anywhere else — not because the versions are equivalent. They are not; 3.1 has more patients.

Marker's question: "isn't parsing 3.1 data with a 2.2 parser dangerous?" — The ETL reads column names, not a version header, and it was verified after the fact: 364,627 subjects, exactly MIMIC-IV v3.1's patient count, and all 546,028 raw admissions survive into base/. The mislabel lands in base/metadata/dataset.json and is corrected in stage 2.6 (normalise.py), which writes dataset.json fresh with dataset_version: "3.1". Stage 2 carries metadata through unchanged.

Erratum · ROOT depth regression, found and fixed 2026-08-20

Every driver had ROOT = Path(__file__).resolve().parents[1], correct when they lived at scripts/*.py. The tree refactor moved them into scripts/{etl,train,evaluate,tools}/, so parents[1] became scripts/ and every default path in every driver was wrong. Fixed to parents[2] across 28 Python drivers, and dirname/.. → dirname/../.. across 6 sweep shell scripts.

Two spellings were in play: parents[1] in 26 files, and .parent.parent in train_motor_aki.py and train_motor_aki_lora.py — the two most important drivers in the project. A grep for one spelling undercounts. Nothing had actually broken, because every completed stage ran before the refactor.

Tests

Trap · spy_run patches globally, by accident of design

It does monkeypatch.setattr(base_meds.subprocess, "run", _fake_run). But base_meds.subprocess is the one global subprocess module object, so patching its run attribute patches it process-wide — which is why the same fixture silently works for meds_reader_db's tests without a second fixture. It is implicit, and it breaks the day either module switches to from subprocess import run.

Every guard test ends assert spy_run == []. Not "it raised" — "it raised before launching". A guard that fires after starting a four-hour job is not a guard. The line passes on correct code either way, so it is there deliberately; deleting it lets a guard-after-launch bug through undetected.

test_run_base_meds_propagates_nonzero_exit does not use spy_run — it installs its own raising fake, because spy_run always returns success.

Not covered: src being a file rather than a directory; non-integer num_shards. Neither matters.

Questions

Scored 4 / 5

Q1 Name two concrete things the tests can do because build_command is pure and run_base_meds is not. Partial

I answered "test it independently" and "check the ordering" — that is one capability and one finding it enables. The two that count: (a) argv is verifiable with no filesystem, binary, or process; (b) it can be diffed against the real CLI's --help without launching it. Re-ask in session 3.

Q2 Counter the claim that capture_output=True would give better logging than dumping to a terminal. Partial

The "blank terminal for hours" reasoning was right, but I skipped the second half: what the codebase does instead. The shell's 2>&1 | tee <logfile> — terminal and file simultaneously, which capturing cannot do. Re-ask in session 3.

Q3 Explain _VERSION_SUBDIR = "2.2" against MIMIC-IV 3.1 data, and name the artifact and the stage that fixes it. Right

Right conclusion, shaky premise — I claimed the versions were equivalent. They are not; the reason is the hardcoded path. And the fix is stage 2.6, not "the next stage" (stage 2 only carries metadata through).

Q4 What class of bug survives if assert spy_run == [] is deleted from every guard test? Correct

A guard that raises after launching the child process. And yes — the tests still pass on correct code, which is why the assertion has to be written deliberately. One wording fix: it asserts the mock was never called, not that it "fails".

Q5 Why does the driver pass Path(sys.executable).with_name(...) rather than relying on shutil.which? Correct

Two virtualenvs split on numpy; resolving from the running interpreter guarantees the console script matches it, whatever PATH says.
